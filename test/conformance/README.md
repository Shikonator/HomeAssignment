# Conformance suite

Golden-fixture tests for the consolidated-book analytics: the touch, the
notional volume bands and the bps price bands.

## Why these are not just more unit tests

Unit tests written alongside an implementation tend to encode that
implementation's assumptions, so they confirm the code does what it does. The
fixtures here are generated by `reference/aggregate_ref.py`, an independent
implementation written from the assignment specification and the comments in
`proto/md/v1/market_data.proto`, deliberately without reading the C++ it
checks. Two implementations, in two languages, agreeing on hand-checkable
numbers is evidence; one implementation agreeing with itself is not.

Python integers are arbitrary precision, which matters: the reference cannot
silently overflow where a naive `int64` implementation does, so it still
produces the correct expected value for cases that break the code under test.

## Layout

    reference/aggregate_ref.py   independent analytics implementation
    reference/gen_fixtures.py    builds the fixtures below
    reference/check_fixtures.py  invariant checks on the generated goldens
    fixtures/*.json              inputs in wire form + expected outputs

Fixture inputs are exchange-style decimal **strings**, not pre-parsed integers,
so a conformance test exercises the whole path: parse -> merge -> analytics.

## Constructed scenarios: the unhealthy paths

Replay proves the adapters agree with a venue behaving *well*. It cannot prove
they react correctly when it does not, because a healthy recording contains no
sequence gaps, no mid-stream snapshots and no rejected subscriptions — and
those paths are precisely what stands between a lost message and a permanently
wrong book.

`fixtures/venue_scenarios.json` holds 16 hand-built frame sequences written
from each venue's documented rules, driven by `replay_conformance_test.cc`.
They are data rather than C++ so a reader can check the sequence against the
venue's documentation without reading the harness.

The one worth naming is
`okx_gap_then_no_change_heartbeat_must_resync`. OKX repeats its sequence number
when nothing moved. If that no-change shortcut is tested *before* continuity, a
gap followed by a heartbeat skips validation entirely and the book diverges
permanently with no error — and since the OKX checksum is deliberately not
implemented, nothing else would catch it. The scenario pins the ordering.

## Replay: the divergence control

Sequence continuity detects **loss**. It cannot detect a stream that is
perfectly sequenced and applied *wrongly* — that is divergence, and the two are
orthogonal. The OKX CRC32 checksum would have covered divergence for one venue,
and was deliberately dropped: it is computed over the feed's own decimal
strings, which cannot survive normalising to `int64` at ingest. Replay is what
replaces it, offline and for every venue that has a recording.

    reference/capture.py            captures a live session from the venue
    reference/gen_replay_golden.py  replays it independently -> expected book
    replay_conformance_test.cc      replays it through the production adapter

Three things keep this from being circular:

* the recording is captured by an **independent client** (a minimal RFC 6455
  implementation over `ssl`+`socket`), not by the aggregator's own recorder. If
  the same code captured and replayed, a systematic capture bug would cancel
  itself out and the test would pass while the adapter was wrong.
* the seeding snapshot is the venue's own REST depth response.
* the expected final book comes from an independent implementation of Binance's
  documented reconciliation rules.

Capturing correctly is itself subtle, and the harness caught one case the first
time it ran: the REST snapshot must be fetched **off** the read loop. Fetching
it inline stalls the reader, so frames that genuinely arrived *during* the
request get stamped after it, and the replay then sees events older than the
snapshot arriving after it — indistinguishable from a sequence break. The
aggregator gets this right by issuing the GET asynchronously on the same
`io_context`; a recording has to reproduce the same ordering to be faithful.

Recordings carry receive timestamps and are replayed in **receive order**, not
file order. The snapshot is written last as a convention; `recv_ts_ns` is what
says when it arrived.

## Published depth, and why the 50M band never fills

`reference/measure_depth.py` fetches one REST snapshot from each venue, merges
them with the reference implementation, and writes `reference/depth_survey.md`.
The measured answer is that the consolidated book spans roughly 100 bps and
holds tens of millions of dollars, not hundreds: the specification's headline
50M band cannot be filled from what these venues publish, and the 200/500/1000
bps price bands lie outside the published ladder entirely.

Both are reported honestly rather than hidden — `fully_filled=false` and
`depth_limited=true` are the correct answers — but they are also the most
suspicious-looking output in the system, so the claim is measured, dated and
reproducible rather than asserted.

## Regenerating

    python3 reference/gen_fixtures.py
    python3 reference/check_fixtures.py

`check_fixtures.py` validates the goldens against properties that hold
independently of how they were computed (ladder ordering, `qty_total ==
sum(by_venue)`, band monotonicity, VWAP bracketed by touch and worst price,
every emitted value fitting in `int64`). A reference with a bug produces
self-consistent nonsense, so the goldens are themselves checked before any C++
is asserted against them.

## What each fixture pins

| fixture | covers |
|---|---|
| `bbo_basic` | small, hand-verifiable; per-venue attribution at the touch; a sweep deeper than the book |
| `deep_50m_sweep` | ~3950 BTC per side so every band up to 50M fills; intermediate `px*qty` reaches 1.1e22 and overflows `int64` by three orders of magnitude |
| `crossed_book` | `best_bid > best_ask` across venues: signed spread, `crossed=true`, bands still walked from each own-side touch |
| `empty_ask_side` | one side absent: `mid`/`spread`/`spread_bps` are 0 and `crossed` is false, never derived from a zero price |
| `empty_book` | no liquidity anywhere; no division by zero |
| `bps_bound_exact` | a level resting exactly on the 50bps bound on both sides, with outward rounding making the bound inclusive symmetrically |
| `venue_filter_binance_okx` | filtered view re-derived from per-level attribution; excluding a venue moves the touch and un-crosses the book |
| `venue_filter_unfiltered_baseline` | the same book unfiltered, so the filtered view can be asserted as a strict re-derivation |

Two generated corpora sit alongside them:

| corpus | covers |
|---|---|
| `parser_corpus` | 465 `ParseFixed` cases: venue-shaped values, both signs, elided parts, leading zeros, truncation past the 8th decimal, the exact `INT64_MAX` boundary at 92233720368.54775807, integer overflow, exponent notation, embedded NUL, non-ASCII digits, and 400 randomised decimals |
| `replay_binance_btcusdt_golden` | the expected final book after replaying a real recorded Binance session |
| `random_books_corpus` | 180 randomised books with prices and quantities carrying digits in every decimal place, and notional targets placed **exactly on cumulative level boundaries** and one unit either side — the case a single-pass band walk is most likely to get wrong |

Every fixture except `empty_book` carries an intermediate `px*qty` above
`INT64_MAX`, so any of them catches a 64-bit multiply; `deep_50m_sweep` also
catches a 128-bit multiply that narrows too early.
